# KERNEL.md — конституция кернел-режимов (обязательно к прочтению в новых сессиях)

Документ для ИИ-сессий, которые добавляют или меняют функции чита. Его задача —
чтобы новые функции **не сломали кернел-режимы (FT/RT-Dev/RT-Hook)** и не «рассекретили»
процесс. Если коротко: вся работа с памятью игры идёт через ОДИН выбранный
пользователем транспорт, и `/proc/<pid>/mem` в кернел-режимах не открывается
НИКОГДА — ни для чтения, ни для записи, ни «на минутку».

Обновляйте этот файл, если меняете архитектуру доступа к памяти.

---

## 1. Золотое правило

> В кернел-режимах (FT-Драйвер / RT-Dev / RT-Hook) процесс чита не
> открывает `/proc/<pid игры>/mem` и не использует `process_vm_readv` /
> `process_vm_writev` / `ptrace`. Вся память игры — через `g_mem`
> (выбранный транспорт). `/proc/<pid>/maps` — можно и нужно (это карта
> регионов, а не память; без неё не найти базу libil2cpp ни в одном режиме).

Почему: (а) fd `/proc/<pid>/mem` светится в `/proc/<self>/fd` чита — его
видят античиты и ручные проверки (`ls -l /proc/<pid>/fd/*`); (б) прямой
доступ часто закрыт там, где драйвер работает, — функция молча ломалась
(прецедент: сайлент-аим, коммит f454180).

## 2. Архитектура доступа к памяти (не менять без веской причины)

```
фичи (ESP, аим, фарм, лут, viewmodel, сайлент …)
        │  только через:
        ▼
memio::Reader g_mem            (jni/src/mem_io.h, объект в game.cpp)
        │  transport_ — ровно один указатель, назначается ОДИН РАЗ
        ▼
memio::Transport (интерфейс: open/close/read_once/write_once)
        ├── ProcfsTransport   «Прямое чтение»  только process_vm_readv/writev
        │                    (raw syscall): /proc/<pid>/mem не открывается
        │                    вообще (ни на чтение, ни на запись); запрет
        │                    syscall политикой = доступа нет, bind отклонён —
        │                    фоллбэка на pread/pwrite нет)
        ├── KernelTransport   «FT-Драйвер»     сокет bing/gongchuang (kernel_io.h)
        ├── RtDevTransport    «RT-Dev»          /dev/[A-GNY]{1,6}, ioctl 0x801/0x802
        └── RtHookTransport   «RT-Hook»         syscall ioctl(-1, 0x259/0x25a)
```

- Назначение: `modesel::RunModeSelect()` → `esp_set_mem_backend()` →
  `g_mem.set_transport(t)` — ЕДИНСТВЕННОЕ место назначения. Вызывается до
  первого bind: поток привязки (`start_attach_thread()`) стартует строго
  ПОСЛЕ экрана выбора (main.cpp).
- Исключение — одноразовые CLI-процессы `dump` (`metadata_dump.h`) и `skel`
  (`skeleton_diag.h`) из Termux: там `esp_set_mem_backend` вызывается с
  режимом из аргумента, `.mode` или (legacy) трейлера конфига до первого
  bind, изучение транспорта — явным шагом `PrepareOneShotBackend` там же,
  после чего процесс завершается (GUI-путь в нём не выполняется).
  Правило то же: один транспорт на жизнь процесса, никаких переключений
  и фоллбэков.
- После назначения `transport_` не меняется. Ошибки чтения НЕ переключают
  транспорт: серия отказов → rebind ТЕМ ЖЕ транспортом (`note_fail`),
  не помогло — привязка снимается, attach-поток перепривязывается тем же
  транспортом. Никакого фоллбэка на procfs в кернел-режимах НЕТ — это
  осознанное решение пользователя, не баг.
- `invalidate()`/rescan драйверов возможен только тапом по кнопке на экране
  выбора режима (до входа в игру).

## 3. Справочник режимов (проверено реверсом, детали в reversing/NOTES_*.md)

| Режим | Класс драйвера | Механизм | Запрос | Коды |
|---|---|---|---|---|
| Прямое чтение | — | только `process_vm_readv`/`process_vm_writev` (raw syscall); `/proc/<pid>/mem` не используется совсем, фоллбэка нет; правки только по rw-памяти | — | — |
| FT | bing_rw / gongchuang (drivers.7z) | socket(сем.,4,0); команды getsockopt ИЛИ ioctl (поколение 5.10) | `DriverRwReq` 0x28: pid,pad,addr,size,user_buf,magic=0x1337 | auth 0x300, read 0x301, write 0x302; gong: attach 2, vm 4, pte 5/6 |
| RT-Dev | RTkernel (`rt dev Драйвера root cheat.zip`) | char-устройство `/dev/[A-GNY]{1,6}` + ioctl | `RtDevCopyMem` 0x20: pid,pad,addr,buffer,size (не через границу 4К — транспорт чанкует сам) | read 0x801, write 0x802; base 0x803 |
| RT-Hook | hookdd/gynhdd (`RT-hook.7z`) | перехват syscall `ioctl`, без сокета и `/dev`-узла | `RtHookCopyMem` 0x20: pid,pad,addr,buffer,size (transport чанкует по 4К) | read 0x259, write 0x25a |

Особенности, которые нельзя забыть:
- FT: транспорт выучивается на месте (`detect_protocol`: подсемейство bing
  или gongchuang, доставка getsockopt/ioctl `use_ioctl_`, коды команд).
  Перед командами отправляется auth-пароль (0x300, 0x31 байт). Сокеты
  драйвера живут всё время процесса — `close()` у транспорта логический
  (отвязка pid), СОКЕТЫ НЕ ЗАКРЫВАТЬ.
- FT getsockopt: level = pid целевого процесса и он НЕ должен быть
  SOL_SOCKET, иначе команда уйдёт в generic-обработчик сокета (ENOPROTOOPT).
- RT-Dev: `init_module` вызывает `get_rand_str`; во всех 23 модулях имя
  root-only char-узла содержит 1..6 символов из `A..G`, `N`, `Y` — паттерн
  `/dev/[A-GNY]{1,6}`. Транспорт ищет только его и подтверждает
  чтением/записью собственной памяти; подтверждённый fd живёт до завершения
  процесса.
- RT-Hook: модуль заменяет обработчик syscall `ioctl` на arm64. Транспорт
  вызывает `ioctl(-1, 0x259/0x25a, &req)`, не открывает ни сокет, ни `/dev`;
  наличие подтверждается пробой чтения собственной памяти. Не смешивать его
  с RT-Dev: у них разные discovery и ABI.
- Все транспорты сами снимают TBI/MTE-метку адреса (`kAddressTagMask`) и
  сами чанкуют запросы, где нужно. Вызывающий передаёт сырой адрес и размер.
- Размеры структур защищены `static_assert` — при правке раскладки сборка
  упадёт, это правильно.

## 4. Инварианты для НОВОГО кода (чек-лист перед коммитом)

1. **Читать память игры**: `g_mem.read()` (кадровый путь, блочный кэш) или
   `g_mem.read_quiet()` (мимо кэша — для фоновых потоков и «пробных»
   чтений, где отказ ожидаем). **Писать**: `g_mem.write()`.
2. **Новый фоновый поток** с доступом к памяти — по образцу сайлент-аима:
   `esp_silent_target(pid)` (привязка жива и это тот pid) →
   `esp_silent_read/write` (game.h/game.cpp). Не открывать свои fd.
   Перед доступом всегда проверять `g_mem.bound()`.
   Существующие писатели «вечного дня» и фрикама (game.cpp) идут через
   `wr_buf` → `g_mem.write`: это ТОТ ЖЕ канал (один выбранный транспорт),
   а ворота `open_/pid_` Reader::write проверяет внутри — отдельного fd и
   обхода транспорта там нет. Новые потоки всё равно пишите через
   `esp_silent_*`.
3. **Новая цель/pid** — только через `esp_init()` (attach-поток, process.cpp).
   Никогда не открывать память процесса самостоятельно.
4. **Не звать** `open("/proc/%d/mem")`, `pread/pwrite` по чужой памяти,
   `process_vm_*`, `ptrace`. Разрешённые исключения — ровно три:
   `ProcfsTransport` (он и есть режим «Прямое чтение»), диагностика
   `--check-driver` (открывает `/proc/1/mem` и сразу закрывает) и
   `/proc/<pid>/maps` (карта регионов, во всех режимах).
5. **Не добавлять** авто-выбор/переключение транспорта после старта,
   «умный» фоллбэк на procfs при ошибках, повторный `detect_protocol`
   из игрового цикла. Слепые пробы неизвестных кодов команд драйвера
   могут потревожить драйвер — разрешены только три явных места:
   экран выбора режима, `PrepareOneShotBackend` в one-shot CLI
   (`dump`/`skel`, где экрана нет) и диагностика
   `--check-driver`/`--scan-driver`. `Transport::open` детект не делает
   никогда — только переиспользует выученное.
6. **Не кэшировать** `Transport*` или копии `Reader` — только `g_mem`
   (указатель может смениться между сессиями привязки).
7. Порядок старта в main() не менять: экран выбора → `start_attach_thread()`.
   Всё, что читает память, — после этого.
8. Аудит перед коммитом — единственная строка, которая должна найти
   ТОЛЬКО `mem_io.h:161` (это сам ProcfsTransport) и комментарии:
   ```
   grep -rn '"/proc/%d/mem"\|process_vm_readv\|process_vm_writev\|PTRACE_ATTACH\|PTRACE_TRACEME' jni/src jni/include
   ```
   Любой новый хит вне mem_io.h/комментариев — ошибка архитектуры.
   На устройстве: `ls -l /proc/<pid чита>/fd/*` — в кернел-режимах
   НЕ должно быть `-> /proc/<pid игры>/mem` (процесс скрыт: «vold»).
9. Хост-проверка синтаксиса правленных файлов + CI (основной артефакт
   `benzware.sh`). При изменении RT-Dev:
   `python3 scripts/verify_rt_dev_archive.py`
   должен подтвердить все модули архива. `--check-driver` из Termux — коды выхода:
   0 = драйвер работает, 1 = ничего не найдено, 2 = драйвер есть, коды
   не подтверждены. `--scan-driver` — полный скан кодов 0..0x7FF
   (только Termux, до маскировки). `dump` из Termux (игра запущена) —
   коды выхода: 0 = метадата сохранена, 1 = игра не найдена / транспорт
   не привязался, 2 = привязка есть, метадата не найдена, 3 = выгружено
   с ошибками (файлы `*.partial`). `skel` из Termux (игра запущена) —
   коды выхода: 0 = скелеты строятся, 1 = игра не найдена / транспорт
   не привязался, 2 = скелет не собрался ни у одного игрока,
   3 = привязка не подтвердила класс (`esp_init` отказал).
10. **Писать — только по расхождению.** Перед правкой поля его читают
    (`rd_exact` — кадровый путь, `rd_fresh`/`read_quiet`/`esp_silent_read` —
    фоновые потоки) и пропускают запись, если там уже лежит желаемое.
    Сверяться со СВЕЖИМ значением, а не с тем, что мы помним о прошлом кадре:
    поля общие с игрой, вернёт своё — запись обязана вернуться. Включённая и
    ничего не меняющая функция не производит ни одной записи. Исключения —
    только поля, которые по смыслу меняются каждый кадр (матрицы фрикама в
    полёте, стик автофарма); список — в DETECTION.md.
11. **Всё, что установлено вне процесса, обязано сниматься само.** Правило
    iptables, временный файл, `EVIOCGRAB`, `UI_DEV_CREATE` — переживают
    `_exit`, висящее «на устройстве» состояние потом ищут как признак чита.
    Значит: снимать не только в `apply(false)`/деструкторе, но и по всем
    ловуемым сигналам (`FakeLag::unblockRaw()` — `fork`+`exec` без malloc и
    без join), и по дедлайну выхода в `main.cpp`, и предварительной чисткой
    перед установкой. Не поймать только SIGKILL/SIGSTOP — это надо указать в
    комментарии рядом.
12. **Инжектированное устройство ввода не должно выглядеть инжектором.**
    `uinput`-палец («Аим → Тач») обязан нести name/phys/bustype/vendor/product
    настоящего тачскрина (`EVIOCGNAME`/`EVIOCGPHYS`/`EVIOCGID` по уже
    открытому fd), а не `rand()`: список ввода читает любое приложение без
    разрешений, и случайное имя — подпись, по которой функцию находят.
13. **Скины: `Oxide.WeaponPiece` — SyncVar направления server→client.**
    Писать в него можно (наружу значение не уходит), но игра вправе вернуть
    своё в любой момент: запись только «по расхождению со свежим чтением»
    (п. 10) и с возвратом оригинала при выключении. В `PlayerWeapon` лежат
    ДВЕ копии `WeaponPiece` — SyncVar (релиз +0x110, бета +0x130) и рабочая
    (релиз +0xC0, бета +0xD0); писать нужно только в SyncVar, рабочая не
    участвует. Третья точка с тем же индексом — `PlayerFPWeaponView` (+0x28):
    это копия, ИЗ КОТОРОЙ FP-вьюха уже построена; её не пишем, а читаем как
    диагноз «пересобралось или нет» (`SkinUiInfo.fp_stale`).
    Значение `Skin` — данные, а не доказательство адреса: у ствола без скина там
    лежит отрицательное число, поэтому проверять прочитанное диапазоном нельзя
    (именно такая проверка ставила исправный билд на «поле скина не читается»).
    Адрес доказывается структурой головы piece: `Enabled` и `Loaded` обязаны быть
    0/1, `Number` — неотрицательным коротким id. Голова читается одним запросом
    (`skinchanger::read_piece`, 8 байт) и она же различает «транспорт не читает»
    (стадия 14) и «оффсеты не от этого билда» (стадия 15).
14. **RVA TypeInfo-слоты — якорь одноразовый: база libil2cpp может быть не от
    живого образа.** Слот — абсолютный адрес .data-ячейки, верный только для
    билда дампа И только от правильной базы. База плавает без всякого
    обновления игры: пакет перезапускается через exec (pid сохраняется), в
    карте остаётся старый «(deleted)» образ с мёртвыми метаданными, а во время
    загрузки статика живого образа ещё NULL — привязка в этот момент берёт
    первый читаемый кандидат (game.cpp, package_verified_release). Устройство
    это подтвердило (skin.log): в одной сессии все типы скинов деградировали в
    «other» при НЕИЗМЕННОЙ версии игры, а цепочка, запись индекса и readback
    продолжали работать — они позиционно независимы (игрок находится
    мирочиталкой, классы сверяются по имени от самого объекта). Поэтому
    (а) любой признак от слота обязан иметь позиционно-независимый резерв —
    точное имя класса (`skinchanger::klass_name_is`: побайтовое чтение
    klass->name от klass самого объекта, сравнение вместе с NUL, БЕЗ допуска
    по instance_size — у родственных классов он схлопнул бы все типы в один);
    (б) промах слота — не доказательство, что объект другого класса, ровно как
    значение поля не доказывает адрес (п. 13); (в) следствие для диагноза: если
    тип не распознан, ready неизмерим, и утверждать «ассета нет на устройстве»
    нельзя — skin.log и меню говорят «тип не распознан — перезапустите игру и
    чит» (viewmodel.h, `skin_kind_identified`).
15. **У PlayerWeapon ДВЕ копии WeaponPiece, и вьюха строится из второй;
    `Enabled` не трогать никогда.** Проверено дизассемблером дампа 11966
    (полный граф вызовов — в комментарии NB у `PLAYERWEAPON_PIECE_LOCAL` в
    game_offsets.h): SyncVar-копия `+0x110` нужна серверным string-RPC, phW и
    OnStartClient, а рабочая копия `+0xC0` (пишется только pMd) — то, из чего
    hbr.pMZ/pMj на каждом дроу подают piece в FPManager.Kxi → CreateFPWeapon →
    XZE/MjH собирают FP-вьюху. Запись скина только в SyncVar (как было до
    f5652b1) на устройстве дала 17 циклов «применено» и ноль пересборок:
    никто из строителей вьюхи SyncVar не читает. Трюк «Enabled 1→0→1 как
    пересборка» опровергнут дважды: Enabled никто не поллит (SyncVar-хук pFR —
    пустой ret), а ноль в нём — яд: XLy возвращает false, а d__69/MjH при
    Enabled==0 уходят в Release+KxS и прячут ствол. Пересборку вьюхи делает
    ТОЛЬКО игра на своих событиях (дроу/холстер, смена ствола, спавн);
    внешний процесс функции игры не зовёт — поэтому инвариант скинченджера:
    писать Skin/SkinLevel в обе копии, Enabled не писать никогда, а
    «пересборка» в меню/CLI (`esp_skin_request_rebuild`) означает лишь
    немедленную перезапись обеих копий даже без расхождения. Валидация копии
    +0xC0 — ЩАДЯЩАЯ (только Enabled обязан быть bool): собственный путь дроу
    игры смотрит лишь Enabled, а Loaded/Number в рабочей копии на устройстве
    оказались неканоническими — строгая проверка вечно парковала билд на
    «стадия 21», тогда как SyncVar-копия остаётся строгой. Сырая голова
    рабочей копии (hex) уходит в skin.log при любом отклонении от дампа.
    Устройство (skin.log, сборка 105f082) dopeчислило картину: между дроу
    рабочая копия держит «пустую» piece {Enabled=0, Number=-1, Skin=-1} —
    игра гасит её на холстере и НЕ восстанавливает на дроу, поэтому простой
    холстер/дроу вьюху не пересобирает; рабочие триггеры — RPC насадок/модов
    (phW читает SyncVar живьём -> Kxi) и спавн/подбор ствола (OnStartClient).
16. **Докачка ассетов скинов автоматическая — «скачай скин в игре» не говорим
    нигде.** Дизассемблер dump11966: любая сборка визуала (hbB.VsH -> VkM ->
    VkF 0x6CDAFA4) на неизвестную ссылку (hbG.Vqs ->
    ResourceDownloadLedger.get_IsKnown == false) одноразово запускает Vkp ->
    <RefreshAfterCatalogAsync>d__39 (hbO.Vqi — обновление каталога) и оставляет
    плейсхолдер (get_RequiresPlaceholder -> Vky). ITickable hbB.Tick доводит
    остальное сам: каждые 250 мс Vkh ретраит плейсхолдеры той же сборкой, раз
    в 1 с VkX/Vkl/Vkn отбирает неизвестные ссылки ближних визуалов (80 м,
    top-64; FP-вьюха ствола всегда в 0 м) и ставит их в приоритетную очередь
    hbw (реализация hba — resourceDownloadService, статусы SkinDownloadState/
    SkinDownloadSummary, таймаут 5000 мс). Ручное «покрутить превью в
    магазине» не нужно — достаточно одной пересборки из нашего индекса
    (триггеры — п. 15). Поэтому ready==false («ассет не запрашивался») —
    признак, что сборки ещё не было, а не вина пользователя: вердикт меню,
    skin.log и skin_probe говорят «докачается сам». Полный граф с RVA — блок
    «АССЕТЫ КАЧАЮТСЯ САМИ» в шапке skin_changer_memory.h.

22. **Сборка вьюхи может бросить исключение, и оно отравляет FPManager на

    MoveNext 0x68EF65C) НЕ обёрнут в try/catch, а бросить внутри есть чему:
    XZN 0x7C8DFDC проверяет Skin по длине ItemData.skinData (IndexOR
    0x7C8E274) и record по Number (NRE 0x7C8E270), хвост сборки дважды
    bounds-check'ит Number по prefabTable (0x68EFD9C -> IndexOR 0x68F0420,
    0x68EFCF4 -> IndexOR 0x68F046C), instantiate/LoadAssetAsync тоже могут
    бросить. Ключевая деталь — ПОРЯДОК: блок ASSEMBLY 0x68EFE84 сначала

    SetActive(false), и лишь потом XZE 0x7C8F424 грузит визуал; On_Draw
    (слот vtable 17, 0x68FD250: uhq=1, Item=аргумент) живёт ПОСЛЕ всех
    точек броска. Исключение оставляет панцирь: _currentWeapon жив, но
    uhq==0 и Item==null — нарушение здорового инварианта (FDN слот 10
    0x68FCD10 гасит оба вместе, On_Draw ставит оба вместе: uhq==1 <=>
    Item!=null). Дальше каждый дроу обречён: блок сборки уничтожает и
    обнуляет _currentWeapon (Destroy 0xCD46DF0 -> null 0x68EFC9C) ТОЛЬКО
    на здоровом пути до хвоста, а с панцирём гейты 0x68EF940 (uhq==0 ->
    не холстер; Enabled==1 -> сборка) снова идут в сборку, которая снова
    падает на том же скине — FPManager один на все стволы, поэтому
    ломается всё оружие сразу. Перезайти на сервер чинит именно потому,
    что пересоздаёт FPManager. Меню «нет скинов» — наш собственный резолв
    честно падает на стадии 9 (Item==null у панциря). ПОПРАВКА ДОКТРИНЫ
    п. 21: утверждение «CreateFPWeapon смотрит только Enabled» неверно —
    Number bounds-check'ится дважды (см. выше), хвост индексирует
    prefabTable по Number (+0x3a), а не по Skin; relaxed-валидация рабочей
    копии остаётся верной (мусорный Number игра обработает своим броском,

    только после kShellWatchTicks = 450 тиков × 100 мс = 45 с

    счётчик), сброс одноразовый на эпизод (reset_armed_), взводится
    обратно только успешным резолвом; ложное срабатывание на очень
    медленной закачке безопасно — это лишняя пересборка плюс карантин,
    который снимается сменой индекса. Обеззараживание:

23. **«У предмета нет скинов» на популярных стволах — не отсутствие скинов,
    а предел списка: skinData Томпсона/Дезерт Игла/Самопала длиннее прежних
    24 позиций, и общая стадия 12 врала. Предел поднят до 64, длинный массив
    получил честную стадию 27.** Устройство после §4.22 (сборка PR #4):
    отравление ушло — сброс и карантин вернули скины остальным стволам, но
    «на многих нет: Томпсон, Самопал, Дезерт Игл и другие оружия, на них
    скины не работают, пишет "у оружия нет скинов"». Механика вранья:
    резолв проверял `length <= 0 || length > kMaxSkins` одной стадией 12
    (SkinBlock::NoSkins, «У предмета нет скинов»), kMaxSkins =
    kSkinEntryMax = 24 с доктриной «массив короткий, больше меню не нужно».
    Для ствола, чьи скины видны в самой игре (игровое скин-UI читает тот же
    ItemData.skinData +0xD0 — установлено ранее), «нет скинов» может быть
    только враньём: нечитаемый массив дал бы стадию 11, мёртвый ItemData —
    стадию 10. Остаётся единственный неотличимый случай — length > 24.
    Починка: kSkinEntryMax/kMaxSkins 24 -> 64 = SKIN_INDEX_MAX + 1 (sanitize
    всё равно не пускает индекс дальше 63, запись большего — мусор в

    реально доступные строки, поэтому короткий список не подорожал);
    стадия 12 разделена: length <= 0 или нечитаемая длина — по-прежнему 12
    («скинов нет»), length > 64 — новая стадия 27 (SkinBlock::TooManySkins,
    «У предмета больше скинов, чем вмещает список»): другая причина обязана
    звучать иначе, иначе следующий пересмотр предела снова пройдёт под
    вывеской «нет скинов». Это, скорее всего, НЕ новое состояние: стволы с
    >24 скинов не работали всегда, но до §4.22 глобальная поломка это
    маскировала (точное подтверждение — skin.log устройства: строка «!! ...
    (стадия 12: ...)" на Томпсоне в старой сборке). Группировка обновлена
    (27 стадий -> 11 причин), хост-тест test_long_skin_array_is_not_no_skins
    (30 позиций резолвятся, 65 -> стадия 27 и ноль записей, 0 -> стадия 12).
    Граница честности: если skin.log новой сборки всё-таки покажет на этих
    стволах стадию 11 (массив не читается вовсе), гипотеза предела неверна
    и искать надо в цепочке Item/ItemData конкретного ствола.

24. **Отравление лука: у FPBow.FDN NRE на погашенном PlayerEventHandler, а

    блокирует каждый дроу любого ствола, и старый детектор его не видел.**
    Устройство после §4.22+§4.23 (сборка ee906ca, PR #4): «баг пропал, на
    других оружиях скины теперь работают», но «попробовал применить скин на
    лук — не отобразился, и дальше на других перестало применяться». Лог v16
    обрывается на «применено wooden.bow» (+144.1 с): отравленный хвост молчал
    — дедуп блока («В руках пусто» уже был напечатан) глотал его целиком, а
    детектор §4.22 не сработал ни разу. Реверс (dump11966) объясняет обе
    половины. (1) Порядок хранения в ASSEMBLY: _currentWeapon = новый FPObject
    (0x68F00B0) РАНЬШЕ обратных ссылок — Player+0xC0 (0x68F015C) и
    PlayerEventHandler+0xC8 (0x68F01E4, берётся из геттера weaponManager как
    [obj+0x78]); исключение в этом окне (NRE-трамплины 0x68F0480–0x68F0490)
    оставляет панцирь с НУЛЕВОЙ ссылкой, а детектор §4.22 требовал
    ссылку==игрок как часть сигнатуры — слепота. (2) Гейт CreateFPWeapon
    (0x68EF940) на каждом дроу зовёт FDN на _currentWeapon виртуально
    ([klass+0x1D8], 0x68EFA0C) ДО ветки BUILD, которая панцирь уничтожает:
    базовый FPObject.FDN (0x68FCD10) на [this+0xC8]==0 выходит молча
    (0x68FCD58 -> эпилог), Томпсон поэтому просто висел полусобранным, а
    FPBow.FDN (0x68C4970) на том же нуле делает NRE (0x68C4988 -> 0x594D46C)
    — каждый дроу ЛЮБОГО ствола падает ещё до очистки, отравление мгновенное
    и тотальное. Починка: сигнатура панциря — прежняя (живой _currentWeapon,
    Item==0, uhq==0, именной FPManager), а ссылка и обработчик стали
    ДЕТАЛЯМИ (ShellLook). Погашенный PEH — отравление, доказанное структурой
    (здоровая сборка держит его погашенным только субмиллисекундное
    синхронное окно между хранениями): быстрый порог kShellPoisonTicks=20
    (2 с) вместо 450, сброс и карантин те же. Ссылка==игрок при живом PEH —
    медленный путь §4.22 без изменений (здоровая первая закачка ассета).
    Чужая/нулевая ссылка при живом PEH — форма неизвестна: наблюдаем, в
    память игры не пишем. Слепое пятно дедупа закрыто инструментацией:
    skin.log пишет появление панциря с деталями (класс — «FPBow» в строке
    готовый вердикт, ссылка, обработчик) и каждые 10 с ожидания, плюс
    беспанцирное застревание (piece Enabled=1, стадии 7–9, _currentWeapon
    пуст — игра уронила сборку до создания FPObject; сбрасывать нечего,
    строка каждые 10 с). Меню при наблюдении 10+ с показывает «Вьюха
    полусобрана — чит наблюдает» / «Вьюха не собирается — подробности в
    skin.log». Формулировка строки сброса больше не обещает «висел 45+ с»
    (быстрый путь сбрасывает на 2-й секунде). Тесты: 35 (быстрый сброс на
    20-м тике при PEH=0 и карантин), 36 (нулевая ссылка видна и лечится

## 5. Скрытие процесса (stealth.h) — что новый код обязан учитывать

- Процесс маскируется: cmdline = «/system/bin/vold …», comm = vold,
  environ занулён. Исполняемый файл остаётся на диске: удаление во время
  работы запрещено, чтобы `_exit`, SIGKILL или сбой не удаляли запускной файл.
- Поэтому в новом коде:
  - НЕ читать `argv`/`environ`/`getenv` после старта (уничтожены);
  - НЕ оставлять долгоживущих fd к подозрительным объектам (fd-лист —
    поверхность видимости; конфиги открывать-закрывать, как сейчас);
- потомок-трейсер держит ptrace-слот: gdb/Frida получают EPERM — это
  норма, TracerPid != 0 в status — ожидаемо. Он ОБЯЗАН супервизить
  родителя (waitpid + PTRACE_CONT с переправкой сигналов) и вызывается
  ПЕРВЫМ делом в main (до ApplyEarly/потоков). Не «упрощайте» его до
  спящего потомка: seize без супервизии замораживает GUI первым же
  сигналом (сигнал-стоп ждёт трейсера вечно) — так было сломано в 7caffec;
  - новые фоновые потоки наследуют comm «vold» — ничего делать не надо.
- `--check-driver`/`--scan-driver` запускаются ДО маскировки (нужен вывод
  в терминал) — не перемещайте их разбор после `stealth::ApplyEarly`.

## 6. Решения пользователя, которые нельзя откатывать

- Четыре кнопки сеткой 2х2 на экране выбора: «Прямое чтение»,
  «FT-Драйвер», «RT-Dev», «RT-Hook»; заголовок «Способ чтения». Без

## 8. Как обычно ломают кернел-режимы (анти-паттерны)

| Не делайте так | Почему |
|---|---|
| «Напрямую быстрее» — `pread` по fd `/proc/<pid>/mem` в новой фиче | fd в списке чита + не работает при закрытом прямом доступе; см. §1 |
| «При ошибке попробую /proc» — фоллбэк | Рассекречивает и нарушает выбор пользователя; драйвер мог отказать по своей причине |
| Кэшировать `&memio::kernel_transport()` в своей фиче | Указатель на транспорт — дело только `esp_set_mem_backend` |
| Перенести `start_attach_thread()` выше экрана выбора | bind до назначения транспорта = привязка через procfs по умолчанию |
| Звать `invalidate()`/rescan из игрового цикла | Пересканирует и меняет протокол на живой сессии |
| Отправлять драйверу «пробные» команды с придуманными кодами | Неизвестный код может потревожить драйвер/античит; изучение — только в трёх явных местах (§4.5) |
| Закрыть «утёкший» сокет FT в `close()` | Сокеты драйвера живут весь процесс; `close()` — только отвязка pid |
| Читать `argv`/свой файл на диске после старта | Маскировка затёрла argv, бинарник удалён (см. §5) |

## 9. Перенос логики из `manes_aim.zip`

- `mem_driver.hpp` из архива использует `open/pread64/pwrite64` для `/proc/<pid>/mem` и в проект не переносится. Все новые чтения/записи остаются на `g_mem` и существующих `esp_mem_aim_*`.
- Архивные `Offsets` и `EspOffsets` по умолчанию нулевые, а scan/projection/visibility в нескольких местах помечены как `[RECONSTRUCTED]`. Не заменять ими рабочую привязку IL2CPP и текущие resolver-ы; точка входа ESP — `esp_get_boxes()` / `esp_get_markers()`.
- `touch_input.cpp` создаёт второй uinput-путь и меняет SELinux/права устройств. Не импортировать его; тач-аим использует уже поднятый `TouchHelperA` (`Touch_Down/Move/Up`) с ориентацией и слотами текущего проекта.
- Разрешённый перенос — чистые таблица имён и математика наведения в `manes_aim_source.h`; helper не открывает fd и не знает о транспорте.
